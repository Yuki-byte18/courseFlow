## 一、一眼看懂

```
┌─────────────────────────────────────────────────────────────────┐
│  前端：一套 React 应用，三组路由                                  │
│  /student/*   学生端     /teacher/*  教师端    /admin/*  管理端   │
└────────────────────────────┬────────────────────────────────────┘
                             │ HTTP / SSE（开发走 Vite 代理，生产走 Nginx 反代）
                             ▼
┌──────────────── 在线层 Online ──── 面向用户 · 同步 · 毫秒~秒 ────────┐
│  api     抢课 / 查课 / 课表 / 大盘接口        毫秒级 · 强一致 · 不可降级│
│  agent   对话、查数据、给卡片                 秒级   · 只读   · 可降级  │
└────────────────────────────┬────────────────────────────────────────┘
                             │ 领域事件（发到 Kafka）
                             ▼
┌──────────────── 近线层 Near-line ── 常驻 · 事件驱动 · 秒级 ─────────┐
│  consumer（Go）   异步批量落库 + 对账补偿                            │
│  Flink 作业        10 秒滚动窗口 → 实时热榜 / 成功率 / 库存大盘      │
└────────────────────────────┬────────────────────────────────────────┘
                             │ 每天凌晨批量抽取
                             ▼
┌──────────────── 离线层 Offline ──── 一次性 · T+1 · 批量 ────────────┐
│  Spark 作业   ODS → DWD → DWS → ADS（Parquet 分区落盘）             │
│  产出         报表数据、课程画像、学生画像                           │
└─────────────────────────────────────────────────────────────────────┘

存储 5 个角色：
  MySQL        业务真相（事务、唯一索引）
  Kafka        事件总线（削峰、解耦、可重放）
  Redis        库存 / 去重 / 限流 / 秒级读数
  Parquet      数仓四层（离线计算的地盘）
  ClickHouse   OLAP 查询服务（大盘和报表来查它）
```

## 二、前端：一套应用，三组路由

### 为什么不做三个独立应用

前端只有一个人写。三个独立应用 = 三套脚手架 + 三套登录 + 三套构建 + 共享组件复制三份。
**而且安全性一点没提升**——真正的权限边界在后端，前端隐藏菜单只是体验。

### 三个角色分别看什么

| 角色 | 路由 | 能做什么 | 数据范围 |
|---|---|---|---|
| **学生** `student` | `/student/*` | 抢课、退课、查余量、看课表、问 Agent | 只能动自己的选课记录 |
| **教师** `teacher` | `/teacher/*` | **只读**：我开的课、选课名单、导出点名册 | 只能看自己开的班次 |
| **教务管理员** `admin` | `/admin/*` | 排课、配轮次、预热库存、补录、看大盘和报表 | 全局 |

### 三件必须记牢的事

**① 教师不能发布抢课。** 不是权限大小问题，是业务逻辑问题——排课要决定时间、教室、容量，
这三样是全局资源，两个老师自己排就会撞车。所以排课是教务处的活，教师只读。

**② 数据隔离必须做在后端，而且是这种方式：**

```go
// ❌ 错：身份从参数传，改个数字就能看别人的
GET /api/v1/offerings?teacher_id=5

// ✅ 对：身份从 JWT 里取，路径带 my- 前缀
GET /api/v1/teacher/my-offerings
GET /api/v1/teacher/offerings/:id/enrollments   // 还要校验这个班次是不是我的
```

越权时返回 **404 而不是 403**——403 等于告诉攻击者"这个资源存在，只是不属于你"。

**③ 一个用户可能有多个角色**（比如研究生导师既是 teacher 又是 student）。
所以 JWT 里存 `roles: []string` 数组，不要存单个 `role` 字符串。

### 页面清单

| 端 | 页面 |
|---|---|
| 学生端 | 选课台（列表+组合筛选+抢课）、我的课表、Agent 对话、登录 |
| 教师端 | 我的开课、选课名单+导出 |
| 管理端 | 课程库、开课班次、批量导入、轮次配置、实时大盘、报表 |

## 三、后端：三层 + Agent

### Agent 归在哪一层？

**归在线层。** 判据是 SLA，不是"是不是 HTTP 服务"：

| | 在线层 | 近线层 | 离线层 |
|---|---|---|---|
| 回答什么问题 | 现在这一刻是什么 | 正在发生什么 | 过去有什么规律 |
| 同步/异步 | 同步（有人在等） | 异步 | 异步 |
| 延迟 | 毫秒 ~ 秒 | 秒 | 分钟 ~ 小时 |

Agent 是同步的、有人在等结果的、回答"现在"的问题——所以它属于在线层。

但它是在线层里的**独立部署单元**，因为有三点不同：

| | `api` | `agent` |
|---|---|---|
| SLA | 毫秒级，**不可降级** | 秒级，**可降级** |
| 挂了会怎样 | 事故 | 功能降级，用户手动选课 |
| 依赖 | Redis / MySQL / Kafka | **+ 外部 LLM（整条链路最脆弱的一环）** |

### 三个常驻进程干什么

**`api`（在线层核心）**

- 抢课、退课、候补
- 课程组合筛选查询（学生端筛选器和 Agent 用的是同一个接口）
- 课表、学分进度
- 教师端两个只读接口
- 管理端全部接口（排课、轮次、预热、补录）
- 大盘 SSE 推送（读 Redis / ClickHouse）
- 签发 Agent 的确认令牌

**不做**：任何离线批处理、任何 LLM 调用、任何 Kafka 消费。

**`consumer`（近线层的 Go 部分）**

- **异步批量落库**：把选课事件批量写进 MySQL（幂等 + 重试 + 死信）
- **对账补偿**：定时核对"Redis 库存 + 已选人数 == 容量"，差额告警并补偿

**不做**：不对外暴露业务接口（只有 `/metrics` 和 `/healthz`），窗口聚合交给 Flink。

> 为什么这块必须是 Go 而不是 Flink？因为它写的是**业务库**，要事务语义、幂等键、
> 业务错误码，还要和在线层共享事件定义。这不是流计算的活。

**`agent`（业务 Agent）**

- 对话入口（SSE 流式输出）
- 把自然语言翻译成结构化过滤参数
- 选前预检（时间冲突 / 先修 / 学分上限）
- 生成**待确认动作**（不执行）
- 解释失败原因（基于真实错误码）
- 评测集跑分

**不做**：不拥有任何写接口、不持有学生凭据、不直接连数据库（工具走 HTTP 调 `api`）。

## 四、存储：5 个角色

| 存储 | 放什么 | 谁写 | 谁读 | 为什么是它 |
|---|---|---|---|---|
| **MySQL** `courseflow` | 学生、课程、班次、选课记录 | 在线层 + Go 消费者 | 在线层 | 事务 + 唯一索引，正确性的最后一道闸 |
| **Kafka** | 选课领域事件 | 在线层 | Go 消费者 + Flink | 削峰、解耦、保留期内可重放 |
| **Redis** | 库存、一人一课、限流令牌、秒级读数、确认令牌 | 在线层 + 消费者 + Flink | 在线层 | 毫秒级 |
| **Parquet** `/warehouse/data/{ods,dwd,dws,ads}` | 数仓四层，按 `dt` 分区 | Spark | Spark | 列式、便宜、就是数仓该有的样子 |
| **ClickHouse** | 实时热榜、离线报表、ADS 结果 | Flink + Spark | `api` | 高并发聚合查询，MySQL 干这个会拖垮 OLTP |

**一条纪律：MySQL 只管事务，不做分析。** 所有报表和画像查询走 ClickHouse。

## 五、一次抢课的完整旅程

```
① 学生点「抢课」
        │
        ▼
② api 收到请求
   ├─ 限流（全局 / 用户 / 课程 三道）
   ├─ 幂等检查（这个幂等键是不是已经处理过）
   ├─ Redis + Lua 原子扣减库存 ←── 这一步决定成败，毫秒级
   │    失败 → 立刻返回「已满」/「重复选课」/「时间冲突」
   └─ 成功 → 发事件到 Kafka，返回「排队中」
        │
        ├──────────────────────────┬───────────────────────────┐
        ▼                          ▼                           ▼
③ Go 消费者                     Flink 作业                  学生前端
   批量 INSERT 业务库             10 秒窗口聚合               轮询 / SSE 查结果
   唯一索引兜底                   写 Redis + ClickHouse
   失败重试 / 死信                 ↓
   定时对账补偿                  管理端大盘实时跳动
        │
        ▼
④ 凌晨 02:00，Spark 批处理
   业务库 → Parquet ODS → DWD → DWS → ADS
        ├─→ ClickHouse（管理端报表能查了）
        ├─→ Agent 上下文（课程画像、学生画像）
        └─→ 回灌在线层（推荐排序、风控特征）
```

**三个关键点：**

- **成败在 Redis，不在 MySQL。** MySQL 是异步补上的，它的职责是"最终一致 + 兜底不超卖"
- **接口 RT 和落库解耦。** 学生拿到的是"排队中"，不是"等数据库写完"
- **离线层不是死胡同。** 它的产出回灌在线层和 Agent——这才叫三层架构，不是三个孤岛

## 六、几个关键设计决策

### ① 后端按"业务域"切目录，不按"三层"切

传统做法是把 `controller/`、`service/`、`dao/` 各建一个顶层目录。但这个项目装不进三层：

| 组件 | 属于三层吗 |
|---|---|
| `nearline`（Kafka 消费者） | ❌ 没有 controller |
| `warehouse`（Spark/Flink 作业） | ❌ 根本没有 controller |
| `platform`（配置/日志/MySQL/Redis/Kafka） | ❌ 被三层依赖，不在层里 |

顶级目录如果叫 `controller/service/dao`，这些东西只能作为平级"异物"塞在旁边，
顶级目录就同时混了三种分类依据。

**所以：顶层按业务域切，三层折叠进每个域里面**（`enrollment/controller.go`、`enrollment/service.go`……）。
三层一个都没少，只是容器换了。

### ② Agent 只读，写操作由前端执行

```
L0 只读    Agent 用只读工具查数据（结果可信，因为来自真实数据库）
L1 代拟    Agent 生成「待确认动作」，不执行
L2 执行    学生点确认 → 【前端】持一次性令牌调用通用抢课接口
```

**为什么写操作不交给 Agent：**

| 理由 | 说明 |
|---|---|
| 凭据归属 | 前端本来就持有学生 session；Agent 代为写就得持有学生凭据，破坏最小权限 |
| 零新代码 | 前端发的请求走的是和手工抢课**完全相同**的接口，幂等/限流/排队/审计全部复用 |
| 结构安全 | Agent 工具集全是只读的，**哪怕 LLM 幻觉或被注入，最坏结果是一张错的卡片，不是一次错的提交** |

### ③ 不做独立网关

"网关"这个**角色**需要，但不用单独起一个进程（Kong / APISIX）。

关键理由：**我们真正需要的限流是"业务语义限流"，而 Nginx 只能做 IP 级限流。**

| 我们需要的限流 | 需要的输入 | Nginx 能做吗 |
|---|---|---|
| 同一用户每秒 5 次抢课 | **用户身份** | ❌ 不知道谁是谁 |
| 同一门热点课总闸 | **课程 ID** | ❌ 不知道是哪门课 |
| 单 IP 连接数上限 | IP | ✅ 能 |

所以分工是 **Nginx 做接入（路由/静态/TLS/IP 级粗限流），Go 中间件做业务治理（鉴权/用户级/课程级限流/熔断）**。
这叫**分层限流：粗的在外，细的在内**。

### ④ 后端一个镜像跑四个进程

`courseflow-backend` 镜像里放 4 个静态二进制：`api` / `consumer` / `agent` / `migrate`，
compose 里用不同 `command` 起不同容器。

**决定性理由：事件版本一致性。**

```
api 写事件 → Kafka → consumer 读事件
```

如果拆成两个镜像就能独立发布，于是很容易出现"api 升到 v1.2 加了字段，consumer 还是 v1.1"。
**一个镜像 = 一个版本 = 版本漂移在物理上不可能发生。**

### ⑤ 全项目只构建 2 个镜像

| 镜像 | 内容 |
|---|---|
| `courseflow-backend` | 4 个 Go 二进制 |
| `courseflow-web` | Nginx + 前端 `dist/` + 反代配置 |

其余（MySQL / Redis / Kafka / ClickHouse / Prometheus / Grafana）直接用官方镜像。

## 七、进程清单

| 进程 | 常驻 | 端口 | 出现阶段 |
|---|---|---|---|
| MySQL | ✅ | 3306 | M0 |
| Redis | ✅ | 6379 | M0 |
| Kafka（KRaft） | ✅ | 9092 | M2 |
| `api` | ✅ | 8080 | M0 |
| `consumer` | ✅ | 9101（仅指标） | M2 |
| Flink（本地模式） | ✅ 按需 | 8081 | M4 |
| ClickHouse | ✅ 按需 | 8123 | M4 |
| `agent` | ✅ | 8082 | M5 |
| Spark | ⏳ 跑批时 | — | M4 |
| Prometheus / Grafana | ✅ | 9090 / 3000 | M3 |
| Nginx（生产） | ✅ | 80 | M6 |
| Vite（开发） | ✅ | 5173 | M0 |

**M0/M1 只需要 3 个进程**：MySQL + Redis + `api`（`kafka.enabled=false` 就不连 Kafka）。
这很重要——头两周别被环境拖住。

**内存账**：全栈常驻约 8.7 GB，Spark 跑批峰值 +4 GB，**16 GB 虚拟机够用**。
做法是 ClickHouse 和 Flink 用 compose `profiles` 按需启动。

## 八、演进路线

| 阶段 | 内容 | 产出 |
|---|---|---|
| **M0** | 骨架、文档、配置、日志、健康检查、compose | 能 build 能启动 |
| **M1** | 业务闭环 v1（朴素实现）+ **性能基线** | 能选课但慢、会锁等待 |
| **M2** | Redis Lua 扣减、Kafka 削峰、幂等、限流排队、多级缓存 | 每步一次压测对比 |
| **M3** | k6 压测体系、Prometheus/Grafana、pprof 调优 | 压测报告 v1 |
| **M4** | 三层架构落地（Spark + Flink + ClickHouse） | 三条链路都有真实数据 |
| **M5** | 业务 Agent（工具 + 护栏 + 评测） | 能对话、能跳转 |
| **M6** | 课程交付：文档、演示、答辩 PPT | 能答辩 |
| **M7** | 简历包装、README 门面、复盘 | 能投 |

**裁剪策略**（时间不够从后往前砍）：Hive/Iceberg → RAG → 多实例验证 → 教师端实时统计。
**绝不砍**：0 超卖、幂等、压测对比数据、三层最小闭环、课程文档。
