# 项目目标（GOALS）

## 一句话

**courseFlow 用"选课抢课"这个真实业务，把五件事串成一个能跑的系统**：高并发后端、前端工程、
在线/近线/离线三层数据架构、AI Agent 接入业务、数据开发。

三个人的课程项目 + 一份能拿出去面试的作品。

---

## 为什么要做成"企业级"而不是玩具

因为玩具项目在面试里撑不过三个追问。

| 玩具项目的写法 | 会被怎么问穿 |
|---|---|
| "我用了 Redis 做缓存" | 缓存击穿怎么处理的？热点 key 怎么发现的？ |
| "我用了 Kafka 削峰" | 积压了多少？消费速率多少？消息重投怎么办？ |
| "我做了微服务" | 为什么拆？拆了之后分布式事务怎么办？ |
| "我上了 Flink" | checkpoint 用的什么状态后端？水位线怎么处理迟到数据？ |

**企业级不是"组件多"，是"每一处都讲得清、测得出"。** 所以本项目的标准是：

> 每个技术点都要有 **① 为什么用 ② 数据 ③ 代价** 三件套。答不上来的，不写进简历。

---

## 五个学习目标

### G1 高并发后端（**主目标，投入最多**）

**要学什么**

- Redis 原子扣减（Lua 脚本）、一人一课去重、幂等键
- Kafka 削峰填谷、批量落库、重试、死信、对账补偿
- 多级限流（Nginx 粗限 + Go 全局/用户/课程三级细限）
- 排队令牌把瞬时洪峰拉平
- 热点识别与隔离、连接池调优、pprof 火焰图

**验收证据**

- 压测报告：基线 vs 优化后的 QPS / p99 / 错误率对比表
- **超卖数 = 0**（用对账脚本证明，不是口头声称）
- 幂等重放测试通过、故障注入后能自愈

---

### G2 前端工程

**要学什么**

- React + TypeScript + Vite 的工程化组织
- 服务端状态管理（TanStack Query）——抢课结果轮询、余量自动刷新
- SSE 实时推送（大盘）
- 一套代码三组路由 + 三角色权限的前端组织方式

**验收证据**

- 学生端 / 教师端 / 管理端共约 11 个页面
- 管理端实时大盘能跟着压测曲线实时跳动（答辩最好看的一屏）

---

### G3 在线 / 近线 / 离线三层架构（**差异化亮点**）

**要学什么**

- 三层各自回答什么问题、延迟量级差在哪个数量级
- 在线层为什么不能做重计算；近线层怎么把计算从在线层搬走
- 离线层的产出怎么**回灌**在线层（推荐、风控特征）

**验收证据**

- 三条链路都有**能跑的代码 + 真实数据产出**
- 每层延迟有实测数字（在线 ms 级、近线秒级、离线分钟级）

---

### G4 AI Agent 接入业务（**差异化亮点**）

**要学什么**

- 把自然语言翻译成结构化查询参数（`text-to-filter`），而不是盲目上向量库
- 工具设计（窄接口、参数白名单、错误语义）
- **写操作的安全边界**：Agent 只读 + 确认卡片 + 前端持令牌执行
- 评测集与指标（工具调用成功率、任务完成率、越权拦截率）
- 没有 API Key 时怎么降级演示

**验收证据**

- 能回答"还有哪些三学分在兴湘教学楼的课"
- 返回结果可点击，直接跳到该课的抢课页
- 一份评测报告

---

### G5 数据开发（**差异化亮点**）

**要学什么**

- 数仓分层建模：ODS → DWD → DWS → ADS，每层解决什么问题
- Spark 做离线计算（Parquet 分区落地）
- Flink 做实时窗口聚合（滚动窗口、水位线、checkpoint）
- ClickHouse 承接 OLAP 查询
- 数据质量校验、ETL 运行日志、重跑幂等

**验收证据**

- 四层表都有真实数据
- 管理端能看历史报表
- 一份"为什么这个数据量要/不要用大数据组件"的判断说明

---

## 一个副目标 + 一个结果

### G6 软件工程课程作业（**有硬截止时间**）

这是副目标，但**时间不可谈判**：中期检查、提交、答辩都有固定日期。

需要交付：需求文档、设计文档、架构图、接口文档、测试报告、压测报告、演示、答辩 PPT。

> **注意 G6 和 G1–G5 的差别**：G1–G5 是"学得多深"，G6 是"必须在某天之前拿出来"。
> 冲突时**优先保 G6**——因为答不上深度只是少个亮点，交不出作业是零分。

### G7 找工作（最终结果）

方向不止后端：**前端、Agent 开发、数据开发**都能讲这个项目。

所以文档里要保留足够的"为什么这样选"的说明——面试时讲的就是这些。

---

## 优先级（吵架时按这个裁决）

```
G6 课程交付（硬截止）
  ↓
G1 高并发后端（主目标）
  ↓
G3 三层架构  ≈  G4 Agent  ≈  G5 数据开发（差异化亮点）
  ↓
G2 前端（支撑，够用就行）
```

时间不够时的**裁剪顺序**（从后往前砍）：

1. Hive / Iceberg 等额外大数据组件 → 砍
2. Agent 的 RAG 向量检索 → 降级为结构化查询
3. 多实例水平扩展验证 → 降级为单机压测 + 理论论证
4. 教师端的实时统计 → 只保留两个数字
5. **绝不砍**：0 超卖、幂等、压测对比数据、三层架构的最小闭环、课程交付文档

## 明确的非目标

| 不做 | 为什么 |
|---|---|
| 对接真实教务系统 / 学校 SSO | 没有权限，也没有必要 |
| 支付、发票、财务 | 与目标无关 |
| 多租户 SaaS、计费 | 过度设计 |
| Kubernetes 集群 | 三个人、单机部署，K8s 会吃掉全部学习时间 |
| 独立 API 网关（Kong/APISIX） | 只有 2 个后端入口，网关解决的问题我们都没有 |
| 微服务拆分 | 模块化单体已经够，拆了只会增加运维成本 |
| 移动端 App | 一个 Web 应用足够 |
| 为了"技术栈好看"再加组件 | 加了就要能讲清原理、代价、实测收益 |

---

## 一句话记住

> **这个项目的价值不在"用了多少组件"，而在于每一个技术点都有数据、有对比、有代价分析。**
> 面试官不关心你搭了几个玩具，他关心你能不能把一件事做到位。
