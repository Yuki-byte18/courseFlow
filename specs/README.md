# specs/ · 规格驱动开发（SDD）

> **先写规格，再写代码。** 这份文档说明规格怎么写、放在哪、谁来管。

## 为什么

三个人并行开发时，最贵的事故不是"代码写错"，而是**"我以为你要的是 A，你要的是 B"**。
规格把分歧提前到写代码之前解决 —— 那时改的成本是几行 markdown，代码写完再改是一个 PR。

规格也是**课程答辩的硬材料**：老师问"你的需求是怎么来的"，你拿得出 `spec.md`；
问"接口契约在哪"，你拿得出 `openapi.yaml`，而不是指着代码说"就在 handler 里"。

## 目录约定

```
specs/
├── README.md                 本文档
├── _template/
│   ├── spec.md               需求规格模板
│   └── openapi.yaml          接口契约模板
├── 001-domain-model/         三位编号 + kebab-case 名称
├── 002-auth/
│   ├── spec.md
│   └── openapi.yaml
└── ...
```

**编号规则**：三位数字递增，**永不复用**。
即使某个规格被废弃，也保留目录并把 `Status` 改成 `deprecated`，编号不回收
（这样 PR 里引用的 `specs/004-xxx` 永远指向同一份东西）。

---

## 状态机

| Status | 含义 | 谁能改成这个状态 |
|---|---|---|
| `draft` | 起草中，随时可能大改 | 作者 |
| `review` | 已提 PR 等评审 | 作者 |
| `approved` | 评审通过，可以开始实现 | 组长 |
| `implementing` | 实现中 | 作者 |
| `implemented` | 已合并，验收通过 | 组长 |
| `deprecated` | 被新规格取代（在文末写"取代者为 NNN"） | 组长 |

---

## 工作流

```
① 写规格     cp -r specs/_template specs/NNN-功能名
             填 spec.md，接口部分填 openapi.yaml
             Status: draft → review

② 提 PR 评审  这个 PR 【只改 specs/】，不写任何实现代码
             在群里 @ 组长和相关模块负责人

③ 评审通过    Status 改成 approved

④ 实现        git switch -c feat/xxx
             写代码 + 写测试（测试用例来自「验收标准」小节）
             Status 改成 implementing

⑤ 提实现 PR   描述里关联 spec 编号
             review 时逐条对照验收标准

⑥ 合并        Status 改成 implemented
```

**为什么规格 PR 和实现 PR 要分开**：
规格 PR 只有几百字 markdown，评审成本极低，可以反复讨论；
混在一起提，reviewer 会被代码淹没，需求分歧就藏过去了。

## 写作要求

### 必须写清楚的五件事

1. **业务不变量** —— 什么东西绝不能被破坏（如"名额不可为负"）
2. **接口契约** —— 请求/响应字段、错误码、幂等语义
3. **边界与异常** —— 空、超限、并发、重复提交、依赖故障
4. **可测量的验收标准** —— 用 Given/When/Then 写，能直接翻译成测试用例
5. **不在本次范围** —— 明确写出"这个规格不管什么"，防止范围蔓延

### 不允许出现的内容

| ❌ 不要写 | 为什么 | ✅ 改成 |
|---|---|---|
| "系统要高性能" | 无法验收 | "抢课接口 p99 ≤ 100ms @ 5000 QPS" |
| "处理好各种异常情况" | 等于没说 | 列出错误码表，每个码一条触发条件 |
| "用 Redis 做缓存" | 这是实现，不是规格 | 规格只写"余量查询 RT ≤ 50ms"，技术选型写进 `docs/DECISIONS` |
| 大段伪代码 | 规格写代码就没人维护了 | 用状态机/流程图/表格描述行为 |

> **判断标准**：一个从没参与过的同学，只读这份规格，能不能写出一个通过验收的实现？
> 能 → 合格。不能 → 继续补。
